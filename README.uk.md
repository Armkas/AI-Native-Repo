> **Don't just give AI more context. Give it a native workspace.**
> **Не просто давайте ШІ більше контексту. Дайте йому нативний робочий простір.**

Стандарт, CLI-генератор та еталонна архітектура для створення репозиторіїв, які AI-агенти для написання коду можуть самостійно розуміти, навігувати, змінювати та перевіряти.

## 🚀 Швидкий старт: CLI-генератор

Вам більше не потрібно копіювати файли вручну. Ми надаємо потужний CLI для миттєвого розгортання AI-Native робочого простору, адаптованого під ваш улюблений Agent Runtime та складність проєкту.

**Виконайте наступну команду в будь-якій порожній директорії:**

```bash
npx ai-native-repo init .
```

### Матриця з 12 шаблонів
CLI в інтерактивному режимі попросить вас вибрати один з варіантів нашої матриці з 12 шаблонів (4 середовища виконання × 3 рівні):

**Крок 1: Виберіть ваше середовище виконання (Agent Runtime)**
- `claude-code`: Чиста екосистема Anthropic (хуки та навички).
- `codex`: Чиста структура агента OpenAI/Codex.
- `cursor`: Оптимізовано для глобального зіставлення файлів `.cursor/rules/*.mdc` редактора Cursor.
- `gemini-cli`: Чисте середовище Google Gemini.

**Крок 2: Виберіть рівень складності**
- `light`: Мінімально необхідний набір файлів контексту (PROJECT_MAP + основні правила) для простих скриптів або прототипів.
- `standard`: За замовчуванням. Повна архітектура Контексту, Контрактів та Правил для продакшн-сервісів.
- `full`: Корпоративний рівень. Standard плюс захист шляхів (файли лише для читання / лише для додавання, через хуки або CI) і перевірка актуальності контексту.

*Або ви можете пропустити запити за допомогою прапорців:*
```bash
npx ai-native-repo init . --runtime cursor --tier standard
npx ai-native-repo init . --runtime claude-code --tier full --lang zh-CN   # en (default) | zh-CN | ja
```

## 🎯 Головна перевага: Подвійна "прогресивна" архітектура (The Dual Progressive Architecture)

Більшість шаблонів промптів зазнають невдачі у складних реальних проєктах із двох причин: **роздування контексту (Context Bloat) призводить до деградації уваги ШІ**, а **високий поріг входу унеможливлює впровадження в наявні репозиторії**. Стандарт AI-Native репозиторію розв'язує обидві проблеми за допомогою подвійної прогресивної архітектури:

### 1. Прогресивне розкриття контексту (Progressive Context Disclosure) — Захист уваги ШІ
> **Context Must Be Earned (Контекст має надаватися за запитом).**

Ніколи не давайте агенту монолітний промпт на 100 000 слів. Глобальна точка входу (`AGENTS.md`) суворо обмежена **< 2 КБ** і виконує роль легкого "авіадиспетчера". Агент розкриває контекст покроково та за потребою:

* **L0: Agent Rules (< 2 КБ)** → Як агент повинен діяти? (Глобальний маршрутизатор і межі)
* **L1: Project Map (< 100 рядків)** → Що це за проєкт і де все розташовано? (Фізична карта)
* **L2: Architecture / Domain** → Яку бізнес-задачу вирішує цей домен?
* **L3: Interface / Contract** → Як компоненти взаємодіють між собою?
* **L4: Invariants / Tests** → Які правила НІКОЛИ не можна порушувати? Як перевіряти?
* **L5: Implementation** → Вихідний код реалізації

**Завантажується лише контекст, необхідний для поточної задачі.** Це заощаджує токени та усуває розсіювання уваги й галюцинації моделі.

### 2. Прогресивне впровадження в репозиторій (Progressive Repository Adoption) — Безшовна міграція для наявних проєктів
> **Не потрібно починати з чистого аркуша. Будь-який наявний проєкт може стати AI-Native за 10 хвилин.**

Вам не потрібно документувати весь застарілий код за одну ніч. Завдяки **моделі рівнів складності (Tiers)** наявний репозиторій адаптується поступово:

* **День 1 (Tier 1: Light) — Налаштування за 10 хвилин**: Жодного переписування коду. Створіть роутер розміром < 2 КБ, дозвольте ШІ просканувати структуру для створення реальної `PROJECT_MAP.md`, та визначте межі в `MANUAL_TASKS.md`. ШІ перестає блукати репозиторієм.
* **День 30 (Tier 2: Standard) — Знання за вимогою**: Документуйте лише те, з чим працюєте. Коли ШІ редагує модуль (наприклад, auth), зафіксуйте `domains/auth.md` у цьому PR і підключіть верифікацію через скіл `verify`.
* **День 90 (Tier 3: Full) — Корпоративні бар'єри**: Коли команда освоїться, увімкніть захист шляхів (read-only / append-only) та автоматичні перевірки свіжості в CI.

## ⚠️ Агностичність до семантики, Обізнаність про середовище, Налаштовуваність під модель

**"Семантика єдина, але середовища виконання фрагментовані."**

Станом на 2026 рік індустрія усвідомила, що створення AI-Native репозиторію вимагає розділення трьох різних рівнів:
1. **Модель / Постачальник моделі (The Model / Model Provider)** (наприклад, OpenAI, Anthropic, Google, DeepSeek, Qwen, Meta, Moonshot, Zhipu, MiniMax): Визначає базову спроможність і здатність до міркування моделі. Ніколи не зашивайте тут конкретну версію моделі — повне зіставлення Runtime × Model Provider див. у [Матриці сумісності моделей](spec/model-compatibility.md).
2. **Середовище виконання агента (The Agent Runtime)** (наприклад, Claude Code, Codex, Gemini CLI, Cursor): Визначає *як* читаються файли, *коли* викликаються навички та *які* хуки виконуються.
3. **Стандарт репозиторію (The Repository Standard)** (наприклад, Контекст, Контракти, Робочі процеси): Єдина глобальна семантична істина вашого проєкту.

У той час як бізнес-семантика вашого проєкту **агностична до моделей** (і OpenAI, і Anthropic зрозуміють файл `docs/domains/voice.md`), вона повинна бути **обізнана про середовище виконання**.
- **Claude Code від Anthropic** очікує наявності `.claude/settings.json` (з фокусом на хуки життєвого циклу).
- **Cursor** очікує наявності `.cursor/rules/*.mdc` (з фокусом на глобальне зіставлення файлів).

**Постачальник моделі ≠ Середовище виконання агента — не об'єднуйте їх в одну вісь.** Жодне середовище виконання не належить одному постачальнику моделі (Cursor і Claude Code можна запускати з Anthropic, OpenAI або сумісними постачальниками на кшталт DeepSeek). Тому постачальник моделі фіксується окремо в [Матриці сумісності моделей](spec/model-compatibility.md), а не стає окремим шаблоном.

### Еталонний репозиторій проти Споживчого
- **Цей репозиторій (Reference)**: Цей GitHub репозиторій є глобальним *Еталонним репозиторієм*. Він містить декілька адаптерів, генератор шаблонів та код CLI.
- **Ваш репозиторій (Consumer)**: Репозиторій, створений через CLI, є *Споживчим репозиторієм*. Він повинен містити рівно **один** адаптер середовища виконання та **один** рівень складності, щоб AI-агент ніколи не плутався в конкуруючих наборах правил.

### Поточні еталонні середовища виконання проти нових
Цей репозиторій вже сьогодні надає повноцінні шаблони для чотирьох **еталонних середовищ виконання**: `claude-code`, `codex`, `gemini-cli`, `cursor`. Інші реальні середовища виконання — Qwen Code, DeepSeek Harness, Windsurf, GitHub Copilot та інші — відстежуються як **нові середовища виконання** в [Матриці сумісності моделей](spec/model-compatibility.md) і можуть отримати статус еталонних, коли їхні конвенції стабілізуються.

## 🏗 8 стовпів AI-Native архітектури

Цей стандарт перетворює репозиторій з "книги, яку ШІ повинен прочитати" на "робочий простір, в якому ШІ може оперувати". Він визначає 8 архітектурних рівнів:

### 1. Контекст (Context - "Що")
*`PROJECT_MAP`, `Domains`, `Architecture`*
Повідомляє ШІ, що з себе представляє система, де знаходяться елементи і чому вони були побудовані саме так.

### 2. Правила (Rules - "Інструкції та обмеження")
*`AGENTS.md`, `CLAUDE.md`, `.cursor/rules/`*
Інструкції для агента та заявлені обмеження. Як код повинен форматуватися, як повинні оброблятися імпорти і які архітектурні межі потрібно дотримуватися.

### 3. Контракти (Contracts - "Як вони пов'язані")
*`Protocols`, `Schemas`, `API Definitions`*
Явні межі між компонентами. AI-агенти покладаються на явні інтерфейси на значущих архітектурних межах набагато більше, ніж люди.

### 4. Навички (Skills - "Як виконати конкретне завдання")
*`SKILL.md`*
Багаторазові, атомарні можливості (наприклад, "Як згенерувати міграцію бази даних у цьому репозиторії").

### 5. Робочі процеси (Workflows - "Як оркеструвати")
*`SOPs`*
Багатокрокові процедури (наприклад, "План -> Перевірка інваріантів -> Реалізація -> Тест -> Верифікація -> Оновлення документації").

### 6. Інструменти (Tools - "Як взаємодіяти зі світом")
*`MCP Servers`, `Deterministic CLI Scripts`*
Структуровані можливості, які агент може використовувати для читання бази даних, отримання логів або компіляції коду.

### 7. Верифікація (Verification - "Докази")
*`Tests`, `Validators`, `Hooks`*
Автоматизоване замикання циклу. Верифікація коду + Верифікація поведінки агента. Робота агента не завершена, поки скрипт-валідатор не поверне код виходу 0.

### 8. Межа Людина/Агент (Human / Agent Boundary - "Бар'єр довіри")
*`MANUAL_TASKS.md`*
Чітке розмежування повноважень: Що ШІ може робити автономно, на що він повинен запитувати дозвіл (наприклад, деплой на продакшн) і що люди повинні робити вручну.

## 📂 Посібник розробника

Якщо ви хочете зробити свій внесок у сам стандарт AI-Native Repository:

```text
AI-Native-Repo/ (Reference Repository)
│
├── spec/                        # Стандарт: Теорії та філософія, що не залежать від інструментів
├── cli/                         # Вихідний код утиліти `npx ai-native-repo`
├── template-source/             # ЄДИНЕ джерело істини для всіх шаблонів
│   ├── common/                  # Спільні документи (Light, Standard, Full)
│   └── runtimes/                # Адаптери середовищ виконання (Claude, Cursor тощо)
│
├── scripts/
│   ├── generate-templates.js    # Збирає матрицю з 12 комбінацій в cli/templates/
│   └── validate.sh              # CI-пайплайн для перевірки цілісності стандарту репозиторію
└── anr.yaml                     # Машинно-читаний маніфест
```
