> **"Вендоры стандартизируют, как ИИ входит в репозиторий. ANR стандартизирует, как сам репозиторий проектируется в качестве долговечного инженерного актива для ИИ-агентов."**

Межагентный стандарт, эталонная архитектура и платформа управления жизненным циклом для структурирования, верификации и поддержки AI-совместимых программных репозиториев.

## 🤔 Нужен ли вам ANR? (Два пути к AI-Friendly репозиторию)

**Вам НЕ обязательно устанавливать ANR, чтобы создать репозиторий, готовый к работе с ИИ.**  
Современные среды выполнения агентов (Claude Code, OpenAI Codex, Cursor, Gemini CLI, Copilot) уже предоставляют нативные инструкции, правила, хуки и навыки. ANR четко разделяет **Исполнительную среду агента (операционную систему)** и **Архитектуру контекста и управление репозиторием (долговечную организацию кодовой базы)**.

### Путь А: Ручная настройка без сторонних утилит (Рекомендуется для соло-разработчиков и прототипов)
Если вы ведете личный проект или небольшой репозиторий, вам не нужен внешний CLI. Просто следуйте ключевым принципам ANR:
1. **Минимальный глобальный роутер**: Держите `AGENTS.md` (или `CLAUDE.md`, `GEMINI.md`) в корне в пределах бюджета `<= 2048 bytes (2 KiB)`. Он служит авиадиспетчером, маршрутизируя к контексту, а не загружая всю энциклопедию проекта в память промпта.
2. **Модульные воркфлоу через Agent Skills**: Оформляйте повторяемые процедуры в открытом формате [Agent Skills](https://agentskills.io) в `.agents/skills/<name>/SKILL.md`.
3. **Структурированные домены и контракты**: Выносите архитектуру и логику в `docs/domains/`, а схемы баз данных и API — в `docs/contracts/`.
4. **Пошаговое раскрытие контекста**: Следите за тем, чтобы агент читал только документацию, относящуюся к текущей задаче.
5. **Детерминированная верификация**: Задайте явные команды сборки и тестирования, выполнение которых обязательно перед объявлением работы завершенной.
6. **Контролируемые границы человека**: Защищайте критические конфигурации и скрипты релиза через хуки или проверки CI.

---

### Путь B: Стандартизированная платформа жизненного цикла (ANR CLI — Для команд и мульти-агентных сред)
При управлении рабочими системами в командах или с несколькими ИИ-агентами ANR предоставляет проверенный автоматизированный каркас:
- **Переносимость между агентами**: Чистое сопоставление единого источника истины (`docs/`, `.agents/skills/`) между Claude Code, Codex, Cursor и Gemini CLI без дублирования правил.
- **Управление мультирепозиториями**: Поддержание единых структурных стандартов, контрактов и прав доступа в десятках микросервисов.
- **Поддержка и эволюция (Day 2)**: Использование `anr update` со слиянием JSON без перезаписи пользовательских настроек, обнаружением устаревших файлов с `--prune`, а также `anr doctor` для аудита битых ссылок и соответствия скиллов.

## 🚀 Быстрый старт: CLI-генератор

Вам больше не нужно копировать файлы вручную. Мы предоставляем мощный CLI для мгновенного развертывания AI-Native рабочего пространства, адаптированного под ваш любимый Agent Runtime и сложность проекта.

**Выполните следующую команду в любой пустой директории:**

```bash
npx ai-native-repo init .
```

### Матрица из 12 шаблонов
CLI в интерактивном режиме попросит вас выбрать один из вариантов нашей матрицы из 12 шаблонов (4 среды исполнения × 3 уровня):

**Шаг 1: Выберите вашу среду исполнения (Agent Runtime)**
- `claude-code`: Чистая экосистема Anthropic (хуки и навыки).
- `codex`: Чистая структура агента OpenAI/Codex.
- `cursor`: Оптимизировано для глобального сопоставления файлов `.cursor/rules/*.mdc` редактора Cursor.
- `gemini-cli`: Чистая среда Google Gemini.

**Шаг 2: Выберите уровень сложности**
- `light`: Минимально необходимый набор файлов контекста (PROJECT_MAP + основные правила) для простых скриптов или прототипов.
- `standard`: По умолчанию. Полная архитектура Контекста, Контрактов и Правил для продакшн-сервисов, с критериями приёмки, планами задач и независимым ревью по рубрике.
- `full`: Защита высокой зрелости. Standard плюс защита путей (файлы только для чтения / только для добавления, через хуки или CI), проверка актуальности контекста и поведенческие оценки контекстного слоя.

*Или вы можете пропустить запросы с помощью флагов:*
```bash
npx ai-native-repo init . --runtime cursor --tier standard
npx ai-native-repo init . --runtime claude-code --tier full --lang zh-CN   # en (default) | zh-CN | ja
```

## 🎯 Главное преимущество: Двойная "прогрессивная" архитектура (The Dual Progressive Architecture)

Большинство шаблонов промптов терпят неудачу в реальных проектах по двум причинам: **раздувание контекста (Context Bloat) приводит к деградации внимания ИИ**, а **высокий порог входа делает невозможным внедрение в существующие репозитории**. Стандарт AI-Native репозитория решает обе проблемы с помощью двойной прогрессивной архитектуры:

### 1. Прогрессивное раскрытие контекста (Progressive Context Disclosure) — Защита внимания ИИ
> **Context Must Be Earned (Контекст должен запрашиваться по мере необходимости).**

Никогда не скармливайте агенту монолитный промпт на 100 000 слов. Глобальная точка входа (`AGENTS.md`) строго ограничена **<= 2048 bytes (2 KiB)** и работает как легковесный "авиадиспетчер". Агент раскрывает контекст послойно и по требованию:

* **L0: Agent Rules (<= 2048 bytes)** → Как агент должен работать? (Глобальный маршрутизатор и границы)
* **L1: Project Map (< 100 строк)** → Что это за проект и где всё находится? (Физическая карта)
* **L2: Architecture / Domain** → Какую бизнес-задачу решает этот домен?
* **L3: Interface / Contract** → Как компоненты взаимодействуют друг с другом?
* **L4: Invariants / Tests** → Какие правила НИКОГДА нельзя нарушать? Как проверять?
* **L5: Implementation** → Исходный код реализации

**Загружается только контекст, необходимый для текущей задачи.** Это снижает расход токенов и устраняет галлюцинации и распыление внимания модели.

### 2. Прогрессивное внедрение в репозиторий (Progressive Repository Adoption) — Бесшовная миграция для существующих проектов
> **Не нужно переписывать всё с нуля. Любой существующий проект может стать AI-Native за 10 минут.**

Вам не нужно документировать весь легаси-код за одну ночь. Благодаря **модели уровней сложности (Tiers)** существующий репозиторий развивается постепенно:

* **День 1 (Tier 1: Light) — Настройка за 10 минут**: Ноль изменений в кодовой базе. Создайте роутер размером < 2 КБ, позвольте ИИ просканировать структуру для создания реальной `PROJECT_MAP.md`, и задайте границы в `MANUAL_TASKS.md`. ИИ перестает блуждать по репозиторию.
* **День 30 (Tier 2: Standard) — Знания по требованию**: Документируйте только то, с чем работаете. Когда ИИ вносит правки в модуль (например, auth), зафиксируйте `domains/auth.md` в этом PR и подключите автотесты через навык `verify`.
* **День 90 (Tier 3: Full) — Корпоративные барьеры**: Когда команда освоится, включите защиту путей (read-only / append-only) и проверки актуальности в CI.

## ⚠️ Агностичность к семантике, Осведомленность о среде, Настраиваемость под модель

**"Семантика едина, но среды исполнения фрагментированы."**

По состоянию на 2026 год индустрия осознала, что создание AI-Native репозитория требует разделения трех различных уровней:
1. **Модель / Поставщик модели (The Model / Model Provider)** (например, OpenAI, Anthropic, Google, DeepSeek, Qwen, Meta, Moonshot, Zhipu, MiniMax): Определяет исходную мощность и способность к рассуждению базовой модели. Никогда не зашивайте здесь конкретную версию модели — полное соответствие Runtime × Model Provider см. в [Матрице совместимости моделей](spec/model-compatibility.md).
2. **Среда исполнения агента (The Agent Runtime)** (например, Claude Code, Codex, Gemini CLI, Cursor): Определяет *как* читаются файлы, *когда* вызываются навыки и *какие* хуки выполняются.
3. **Стандарт репозитория (The Repository Standard)** (например, Контекст, Контракты, Рабочие процессы): Единая глобальная семантическая истина вашего проекта.

В то время как бизнес-семантика вашего проекта **агностична к моделям** (и OpenAI, и Anthropic поймут файл `docs/domains/voice.md`), она должна быть **осведомлена о среде исполнения**.
- **Claude Code от Anthropic** ожидает наличия `.claude/settings.json` (с фокусом на хуки жизненного цикла).
- **Cursor** ожидает наличия `.cursor/rules/*.mdc` (с фокусом на глобальное сопоставление файлов).

**Поставщик модели ≠ Среда исполнения агента — не объединяйте их в одну ось.** Ни одна среда исполнения не принадлежит одному поставщику модели (Cursor и Claude Code можно запускать с Anthropic, OpenAI или совместимыми поставщиками вроде DeepSeek). Поэтому поставщик модели фиксируется отдельно в [Матрице совместимости моделей](spec/model-compatibility.md), а не становится отдельным шаблоном.

### Эталонный репозиторий против Потребительского
- **Этот репозиторий (Reference)**: Этот GitHub репозиторий является глобальным *Эталонным репозиторием*. Он содержит несколько адаптеров, генератор шаблонов и код CLI.
- **Ваш репозиторий (Consumer)**: Репозиторий, созданный через CLI, является *Потребительским репозиторием*. Он должен содержать ровно **один** адаптер среды исполнения и **один** уровень сложности, чтобы AI-агент никогда не путался в конкурирующих наборах правил.

### Текущие эталонные среды исполнения против развивающихся
Этот репозиторий уже сегодня предоставляет полноценные шаблоны для четырёх **эталонных сред исполнения**: `claude-code`, `codex`, `gemini-cli`, `cursor`. Другие реальные среды исполнения — Qwen Code, DeepSeek Harness, Windsurf, GitHub Copilot и другие — отслеживаются как **развивающиеся среды исполнения** в [Матрице совместимости моделей](spec/model-compatibility.md) и могут перейти в статус эталонных по мере стабилизации их конвенций.

## 🏗 8 столпов AI-Native архитектуры

Этот стандарт превращает репозиторий из "книги, которую ИИ должен прочитать" в "рабочее пространство, в котором ИИ может оперировать". Он определяет 8 архитектурных уровней:

### 1. Контекст (Context - "Что")
*`PROJECT_MAP`, `Domains`, `Architecture`*
Сообщает ИИ, что из себя представляет система, где находятся элементы и почему они были построены именно так.

### 2. Правила (Rules - "Инструкции и ограничения")
*`AGENTS.md`, `CLAUDE.md`, `.cursor/rules/`*
Инструкции для агента и заявленные ограничения. Как код должен форматироваться, как должны обрабатываться импорты и какие архитектурные границы нужно соблюдать.

### 3. Контракты (Contracts - "Как они связаны")
*`Protocols`, `Schemas`, `API Definitions`*
Явные границы между компонентами. AI-агенты полагаются на явные интерфейсы на значимых архитектурных границах гораздо больше, чем люди.

### 4. Навыки (Skills - "Как выполнить конкретную задачу")
*`SKILL.md`*
Многоразовые, атомарные возможности (например, "Как сгенерировать миграцию базы данных в этом репозитории").

### 5. Рабочие процессы (Workflows - "Как оркестрировать")
*`SOPs`, `Plans`*
Многошаговые процедуры (например, "Критерии приёмки -> Проверка инвариантов -> Реализация -> Тест -> Верификация -> Ревью -> Обновление документации"), а также версионируемые планы задач в `docs/plans/`, чтобы следующая сессия продолжала работу, а не начинала заново.

### 6. Инструменты (Tools - "Как взаимодействовать с миром")
*`MCP Servers`, `Deterministic CLI Scripts`, `.agents/tools.md`*
Структурированные возможности, которые агент может использовать для чтения базы данных, получения логов или компиляции кода. Каждый инструмент описан в `.agents/tools.md` с уровнем риска, а учётные данные никогда не хранятся в закоммиченной конфигурации.

### 7. Верификация и оценка (Verification & Evaluation - "Доказательства")
*`Tests`, `Validators`, `Hooks`, `Review`, `Evals`*
Автоматизированное замыкание цикла, упорядоченное по надёжности. Сначала детерминированные проверки: работа агента не завершена, пока они не вернут код выхода 0. Только затем **ограниченный LLM-as-a-judge** оценивает то, что не может решить ни одна команда — выполнены ли критерии приёмки, соблюдены ли границы задачи, верна ли ещё документация — по версионируемой рубрике, в независимом контексте, с допустимым ответом `UNKNOWN` и без права отменить проваленную проверку. Поведенческие оценки проверяют, что сам контекстный слой ведёт агентов к правильному поведению.

### 8. Граница Человек/Агент (Human / Agent Boundary - "Барьер доверия")
*`MANUAL_TASKS.md`*
Четкое разграничение полномочий: Что ИИ может делать автономно, на что он должен запрашивать разрешение (например, деплой на продакшн) и что люди должны делать вручную.

## 📂 Руководство разработчика

Если вы хотите внести свой вклад в сам стандарт AI-Native Repository:

```text
AI-Native-Repo/ (Reference Repository)
│
├── spec/                        # Стандарт: Теории и философия, не зависящие от инструментов
├── cli/                         # Исходный код утилиты `npx ai-native-repo`
├── template-source/             # ЕДИНСТВЕННЫЙ источник истины для всех шаблонов
│   ├── common/                  # Общие документы (Light, Standard, Full)
│   └── runtimes/                # Адаптеры сред исполнения (Claude, Cursor и т.д.)
│
├── scripts/
│   ├── generate-templates.js    # Собирает матрицу из 12 комбинаций в cli/templates/
│   └── validate.sh              # CI-пайплайн для проверки целостности стандарта репозитория
└── anr.yaml                     # Машинно-читаемый манифест
```
